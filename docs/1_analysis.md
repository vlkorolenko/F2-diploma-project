# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ ДОСЛІДЖЕННЯ

## 1.3. Аналіз та порівняння існуючих рішень на ринку готових програмних продуктів
У сучасній інженерії безпеки програмного забезпечення на ринку представлено широкий спектр рішень класу SAST та новітніх ШІ-асистентів коду. Для визначення інженерних орієнтирів та обґрунтування власного технологічного вибору було відібрано три релевантні системи-аналоги, які репрезентують різні підходи до аналізу:
1. **SonarQube (SonarSource)** — еталонний представник класичних модульних платформ статичного аналізу якості та безпеки коду.
2. **Checkmarx SAST** — комерційний важковаговий корпоративний сканер, що спеціалізується на глибинному потоковому аналізі вразливостей.
3. **GitHub Copilot / Copilot for Security** — хмарний асистент на базі великих генеративних мовних моделей, що пропонує перевірку та дописування коду.

| Критерій порівняння | SonarQube Community/Enterprise | Checkmarx SAST | GitHub Copilot for Security | Розроблювана гібридна система |

### Аналітичний висновок підрозділу 1.3
Аналіз показав, що класичні сканери (SonarQube, Checkmarx) страждають від надлишкового рівня False Positives, оскільки їхній математичний апарат базується переважно на синтаксичних патернах і не враховує семантику кастомних проєктних перевірок та контекст санітизації. Це призводить до колосальних часових витрат висококваліфікованих інженерів на ручну фільтрацію хибних тривог.

Хмарні генеративні інструменти (GitHub Copilot) мають фундаментальні недоліки: вони не здатні охопити весь міжкласовий контекст Java-проєкту через ліміти контекстного вікна, схильні до галюцинацій та створюють критичні юридичні ризики порушення конфіденційності інтелектуальної власності.

Розроблювана система вирішує ці суперечності завдяки синергії двох технологій: бібліотека Spoon забезпечує детерміновану побудову графа властивостей коду (CPG) та швидке вилучення вузького ланцюжка вразливості (15–30 рядків), а локальна модель через LangChain4j верифікує знахідку без галюцинацій та формує безпечний скомпільований Pull Request без передачі даних за межі корпоративного периметра.

## 1.4. Аналіз обраної предметної області в межах дослідження (модель As-Is)
Сучасний життєвий цикл розробки безпечного програмного забезпечення (SSDLC) вимагає перенесення практик перевірки коду на якомога більш ранні етапи (принцип Shift-Left). Основними акторами предметної області є:
* **Java Software Engineer** — автор коду, зацікавлений у швидкому отриманні інформативного зворотного зв'язку без необхідності витрачати час на перевірку хибних сповіщень.
* **AppSec / Security Engineer** — фахівець з аудиту, відповідальний за відповідність вихідного коду стандартам OWASP Top 10 та CWE/SANS Top 25.
* **Team Lead / Release Manager** — особа, яка приймає рішення щодо схвалення Pull Request та релізу функціоналу.

Базовими сутностями предметної області виступають: сирцевий код Java (`.java`),抽象не синтаксичне дерево (AST), джерело зараження (`Source`), точка вразливого виконання (`Sink`), маршрут витоку (Taint Path), звіт аудиту безпеки та патч виправлення коду.

### Опис ключових процесів за моделлю «Як є» (As-Is):
1. **Процес 1. Статичне сканування у CI/CD:** Розробник виконує push коду. Запускається SonarQube, який аналізує код синтаксичними шаблонами. Сканер виявляє десятки підозрілих викликів методів (наприклад, конкатенація рядків у запитах) і маркує їх як вразливість CWE-89 (SQL Injection). На практиці виявляється, що вхідний параметр уже пройшов валідацію через кастомний фільтр `SecurityUtils.sanitize()`, якого сканер «не помітив».
2. **Процес 2. Ручний тріаж та пошук контексту:** AppSec-фахівець змушений вручну відкривати проєкт в IDE, шукати всі виклики методів через 3–4 класи (`Controller -> Facade -> Service -> Repository`), витрачаючи від 30 хвилин до 2 годин на верифікацію одного сповіщення.
3. **Процес 3. Формування виправлення коду:** У разі виявлення реальної вразливості розробник створює задачу в трекері, вручну переписує метод (наприклад, на `PreparedStatement`), повторно запускає тести та відправляє Pull Request.

### Вузькі місця (Bottlenecks) моделі As-Is:
* До 70% робочого часу команди безпеки витрачається на спростування помилкових попереджень SAST.
* Відсутність наскрізного міжпроцедурного трасування в легковагових сканерах.
* Затримка зворотного зв'язку (Feedback Loop Latency) між написанням коду та його виправленням досягає кількох днів.

## 1.5. Постановка задачі та формування вимог (модель To-Be)

### Концептуальна модель To-Be:
Впровадження розроблюваної системи докорінно трансформує процес аудиту:
1. Розробник надає посилання на GitHub-репозиторій або завантажує ZIP-архів.
2. Система засобами бібліотеки Spoon парсить вихідний код, будує єдиний Code Property Graph (CPG) та ініціює алгоритм Taint Analysis.
3. Замість аналізу всього коду вирізається точний семантичний зріз (Program Slice) розміром 15–30 рядків, що містить повний шлях передачі змінної від `Source` до `Sink`.
4. Зріз передається через локальний фреймворк LangChain4j у локальну LLM (без виходу в інтернет), яка однозначно визначає валідність вразливості та генерує мінімальний патч.
5. Модуль компіляторної валідації перевіряє коректність синтаксису виправленого коду та ініціює відкриття Pull Request.

### Функціональні вимоги (Core Features):
* **F-01:** Завантаження та препроцесинг вихідного коду Java через GitHub API або локальний архів.
* **F-02:** Синтаксичний розбір коду та побудова моделі AST з повним розв'язанням типів за допомогою Spoon.
* **F-03:** Генерація графа потоку керування (CFG) та графа залежностей даних (DFG) у вигляді об'єднаного CPG.
* **F-04:** Виконання міжпроцедурного аналізу потоків зараження (Taint Analysis) за базою правил CWE.
* **F-05:** Алгоритмічне вилучення мінімальних кодових зрізів (Code Slices) критичних ланцюжків.
* **F-06:** Оркестрація локальної LLM через LangChain4j для фільтрації False Positives та генерації патчів.
* **F-07:** Автоматизована компіляторна верифікація згенерованого патчу через внутрішню JVM-пісочницю.
* **F-08:** Візуалізація інтерактивного графа атаки на клієнтському дашборді та експорт Pull Request.

### Нефункціональні вимоги (NFRs):
* **NFR-PERF-01 (Продуктивність):** Час побудови CPG та вилучення зрізу для кодової бази до 500 класів не повинен перевищувати 60 секунд (p95 Latency $\le 60$ с).
* **NFR-PERF-02 (ШІ-інференс):** Час верифікації зрізу та синтезу патчу локальною мовною моделлю на GPU середнього класу (12 GB VRAM) не повинен перевищувати 25 секунд.
* **NFR-SEC-01 (Конфіденційність):** Повна ізоляція контуру аналізу: жоден фрагмент вихідного коду не має передаватися у зовнішні публічні хмарні API (On-Premise комплаєнс).
* **NFR-ACC-01 (Точність):** Рівень False Positive Rate на еталонному наборі тестів OWASP Benchmark v1.2 не повинен перевищувати 15%.
* **NFR-REL-01 (Відмовостійкість):** Асинхронна обробка завдань через чергу Redis із механізмом повторних спроб (Retry Mechanism) у разі тимчасової нестачі пам'яті під час побудови CPG.

### Постановка задачі:
Таким чином, метою кваліфікаційної роботи є проєктування та розробка гібридної системи статичного аудиту безпеки для Java-проєктів на основі Code Property Graph, Taint Analysis та локальних мовних моделей для вирішення задачі істотного зменшення рівня хибних спрацьовувань у процесах DevSecOps та автоматизованого формування верифікованих Pull Request із виправленнями вразливого коду.
