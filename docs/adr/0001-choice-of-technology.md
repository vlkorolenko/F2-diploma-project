# ADR-001: Вибір технологічного стеку для синтаксичного розбору, побудови CPG та слайсингу Java-коду

* **Статус:** Approved (Затверджено)
* **Дата:** 2026-11-12
* **Автор:** Короленко Влад Романович
* **Погоджено:** Жихаревич Володимир Вікторович

---

## 1. Context (Контекст та постановка проблеми)
Для реалізації гібридної системи статичного аудиту необхідно здійснювати глибокий семантичний розбір вихідного коду на мові Java (версії 8–21) безпосередньо в середовищі JVM. Відповідно до специфікації вимог `[SRS-FUN-02]` та `[SRS-FUN-03]`, система повинна будувати єдиний граф властивостей коду (Code Property Graph — CPG), що поєднує AST, CFG та DFG, виконувати алгоритмічний Taint Analysis і вилучати компактні зрізи коду (Program Slicing).

Ключовими технічними вимогами є:
1. Повна підтримка розв'язання типів (Type and Symbol Resolution) для міжкласових викликів.
2. Можливість програмної модифікації AST для інлайн-застосування патчу та перевірки компілятором `[SRS-FUN-07]`.
3. Робота у межах обмежених апаратних ресурсів (до 4 GB RAM на контейнер аналізатора) без необхідності запуску важковагових сторонніх систем керування графовими БД.

---

## 2. Alternatives (Аналіз розглянутих альтернатив)

### Альтернатива 1: Бібліотека JavaParser + JavaSymbolSolver
* **Переваги:** Поширена бібліотека у Java-спільноті, легка вага, швидкий синтаксичний парсинг окремих файлів.
* **Недоліки:** Механізм `JavaSymbolSolver` має нестабільну поведінку на складних багатомодульних проєктах Java 17+, часто втрачає прив'язку типів у разі відсутності скомпільованих `.class` файлів сторонніх бібліотек; відсутній нативний модуль побудови міжпроцедурних CFG.

### Альтернатива 2: Платформа Joern (ShiftLeft CPG) на базі Scala/OverflowDB
* **Переваги:** Повнофункціональна індустріальна платформа побудови CPG з потужною власною мовою запитів CPGQL.
* **Недоліки:** Написана на Scala, вимагає значних обсягів оперативної пам'яті (від 8–16 GB RAM на середніх проєктах), працює як окремий зовнішній важкий демон. Відсутня зручна можливість інлайн-маніпуляції вихідним AST для генерації диференційних патчів через чистий Java API. Високі FinOps-витрати на підтримку інфраструктури.

### Альтернатива 3: Бібліотека Spoon (Inria) у комбінації з графовим рушієм JGraphT (Обране рішення)
* **Переваги:** Спирається на компіляторне ядро Eclipse JDT Core, що забезпечує бездоганне 100% семантичне розв'язання типів для всіх сучасних версій Java. Надає багатий API для двосторонньої модифікації коду (`CtElement.replace()`, AST Transformations). Повністю інтегрується як стандартна Maven-залежність всередині єдиного Spring Boot мікросервісу.
* **Недоліки:** Не містить готового міжпроцедурного Taint-двигуна з коробки, що вимагає власної реалізації алгоритму трасування на базі графової бібліотеки JGraphT.

---

## 3. Decision (Прийняте інженерне рішення)
**Обрано Альтернативу 3:** Використовувати бібліотеку **Spoon 11.1.0** для синтаксичного розбору, побудови AST та розв'язання типів у поєднанні з оптимізованою графовою бібліотекою **JGraphT 1.5.2** для моделювання та обходу CPG.

---

## 4. Consequences (Аналіз архітектурних компромісів та наслідків)

### Позитивні наслідки:
1. **Нативне JVM-середовище:** Відсутність міжпроцесного накладного овергеду (IPC), швидкість аналізу та прямий доступ до об'єктів компілятора в пам'яті.
2. **Висока точність розв'язання типів:** Завдяки JDT Core система коректно відстежує виклики методів-санітизаторів навіть через інтерфейси та спадкування.
3. **Гнучкість синтезу патчів:** Згенерований мовною моделлю код легко замінює відповідний вузол `CtStatement` через Spoon AST API для подальшої валідації компілятором.

### Негативні наслідки та ризики (Trade-offs):
1. **Складність алгоритмічної реалізації:** Необхідність власноруч імплементувати міжпроцедурне зв'язування викликів (Call Graph Construction) та покроковий алгоритм Taint Propagation на базі JGraphT DirectedGraph.
2. **Споживання оперативної пам'яті:** При парсингу великих репозиторіїв (понад 1500 класів) об'єктна модель Spoon AST вимагає до 3–4 GB RAM, що обумовлює необхідність налаштування жорстких лімітів JVM heap (`-Xmx4g`) та використання потокового аналізу за пакетами.
